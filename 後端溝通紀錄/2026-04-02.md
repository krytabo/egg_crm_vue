# 後端溝通紀錄 2026-04-02

## 問題一：convertToOrder 未扣除 WaterBottleDeposit 儲值

### 問題描述

POST /delivery-reports/{id}/convert-to-order 建立訂單後，缺少扣除 WaterBottleDeposit 儲值餘額的步驟，導致：

1. GET /statistics/water-deposits 的 remainingQuantity / remainingAmount 不會減少
2. 客戶的儲值餘額對不上實際送貨紀錄

### 根本原因

orders.service.ts 建立訂單流程：
1. 建立 Order + OrderItem（計算 strandedQuantity）
2. 若 targetType === CUSTOMER，執行 FIFO 扣除 WaterBottleDeposit

convertToOrder 目前只有：
1. 建立 Order + OrderItem（複製 strandedQuantity）
2. ❌ 未執行 WaterBottleDeposit 扣除

### 期望行為

convertToOrder 建立訂單後，補上 WaterBottleDeposit 的 FIFO 扣除（先扣 remainingQuantity，再扣 remainingAmount）。
建議將 orders.service.ts 的扣除邏輯抽成共用方法。

## 問題三：`POST /delivery-reports` 建立出貨報表時，`strandedQuantity` 未正確累計（第二筆從 0 開始）

### 觀察到的行為

**操作步驟 1：**
1. 建立第一筆出貨報表（`POST /delivery-reports`），A 客戶、商品 qty=5、recoveredQty=0
2. 後端回傳：`items[0].strandedQuantity = 5`（正確）
3. 審核通過後轉入新訂單（`POST /delivery-reports/{id}/convert-to-order`）
4. 訂單狀態改為已完成
5. 查詢 `GET /customers/{customerId}/water-bottle-deposits` → `strandedQuantity = 5`（正確）

**操作步驟 2：**
1. 建立第二筆出貨報表（`POST /delivery-reports`），同 A 客戶、同商品、qty=2、recoveredQty=0
2. 後端回傳：`items[0].strandedQuantity = 2`（❌ 錯誤，應為 7）
3. 預期：max(0, 上一筆 strandedQuantity=5 + qty=2 - recoveredQty=0) = **7**
4. 實際：後端計算結果為 2，代表「前一筆滯留」被當成 0

### 後端文件說明的公式

```
strandedQuantity = max(0, 前一筆滯留 + 數量 - 回收數量)
```

### 推測根本原因

`delivery-reports.service.ts` 建立報表 items 時，查詢「前一筆滯留」使用 `reportDate: { lt: ... }` (strictly less than)，導致**同一天**建立的第二筆 DR 找不到第一筆，`previousStranded` 被當成 0。

### 建議修正

`delivery-reports.service.ts`，查詢 `lastItem` 的 where 條件：

```typescript
// 修正前（錯誤）
deliveryReport: {
  reportDate: { lt: new Date(reportDate) },
},

// 修正後
deliveryReport: {
  reportDate: { lte: new Date(reportDate) },
},
```

> 改為 `lte`（less than or equal）即可包含同一天稍早建立的 DR，正確取得前一筆滯留數量。

### 相關 API 與欄位

| API | 欄位 | 說明 |
|-----|------|------|
| `POST /delivery-reports` | `items[].strandedQuantity`（response）| 問題發生位置，第二筆計算錯誤 |
| `GET /delivery-reports/{id}` | `items[].strandedQuantity`（response）| 同上，可查看儲存的值 |
| `GET /customers/{id}/water-bottle-deposits` | `strandedQuantity`（response）| 從最新 OrderItem.strandedQuantity 計算，第二筆 DR 轉入前為 2（錯誤），轉入後訂單完成才變 7 |

### 影響

出貨報表列表中顯示的滯留數量不準確，每次建立新報表時無法正確反映累計未回收數量。

## 問題四：`POST /delivery-reports/{id}/convert-to-order` 轉入訂單後，`WaterBottleDeposit.remainingQuantity` 未被扣除

### 觀察到的行為

A 客戶有儲值 10 桶、儲值金額 1000 元（`WaterBottleDeposit.remainingQuantity = 10`、`remainingAmount = 1000`）

1. 建立出貨報表 qty=5、unitPrice=80 → 轉入新訂單 → 訂單改為已完成
2. 查詢 `GET /customers/{customerId}/water-bottle-deposits`：
   - `remainingQuantity = 10`（❌ 應為 5）
   - `remainingAmount = 1000`（❌ 應為 600）

多次操作後，`remainingQuantity` 與 `remainingAmount` 始終保持為初始值，從未被扣除。

### 根本原因（已確認）

`delivery-reports.service.ts` 的 `convertToOrder()` 方法使用 **`prisma.order.create()` 直接寫入資料庫**，
而非呼叫 `orders.service.ts` 的 `create()` 方法。

因此以下這段扣除邏輯**完全被繞過**，從未執行：

```typescript
// orders.service.ts, 第 242-247 行（一般訂單建立流程）
if (customerId) {
  for (const item of createOrderDto.items) {
    await this.deductWaterBottleDeposit(customerId, item.productId, item.quantity);
  }
}
```

`deductWaterBottleDeposit()` 方法（`orders.service.ts` 第 1162-1251 行）負責 FIFO 扣除：
1. Phase 1：從 `WaterBottleDeposit.remainingQuantity` 扣除
2. Phase 2：若數量不足，再從 `WaterBottleDeposit.remainingAmount` 按單價換算扣除

但 `convertToOrder` 從未呼叫此方法。

### 相關 API 與欄位

| API | 欄位 | 說明 |
|-----|------|------|
| `POST /delivery-reports/{id}/convert-to-order` | — | 問題根源，建立訂單時未觸發儲值扣除 |
| `GET /customers/{id}/water-bottle-deposits` | `remainingQuantity`（response）| 應被扣除但實際未變化 |
| `GET /customers/{id}/water-bottle-deposits` | `remainingAmount`（response）| 同上，剩餘金額應隨出貨量減少但始終不變 |
| `GET /statistics/water-deposits` | `summary.totalRemainingQuantity`（response）| 統計數字因此不準確 |
| `GET /statistics/water-deposits` | `summary.totalRemainingAmount`（response）| 同上，統計剩餘金額不準確 |

### 建議修正

在 `delivery-reports.service.ts` 的 `convertToOrder()` 建立訂單、mark-as-converted 之後，補上 WaterBottleDeposit 扣除：

```typescript
// Mark items as converted
await this.prisma.deliveryReportItem.updateMany({ ... });

// ✅ 補上：扣除儲值（FIFO）
if (firstItem?.customerId) {
  for (const item of selectedItems) {
    await this.deductWaterBottleDeposit(firstItem.customerId, item.productId, item.quantity);
  }
}
```

同時新增 private method `deductWaterBottleDeposit`（直接使用 `this.prisma`，避免與 `OrdersModule` 的 circular dependency）：

```typescript
private async deductWaterBottleDeposit(
  customerId: string,
  productId: string,
  quantity: number,
): Promise<void> {
  const deposits = await this.prisma.waterBottleDeposit.findMany({
    where: {
      customerId,
      productId,
      OR: [{ remainingQuantity: { gt: 0 } }, { remainingAmount: { gt: 0 } }],
    },
    orderBy: { createdAt: 'asc' }, // FIFO
  });

  let remaining = quantity;

  // Phase 1: 扣除 remainingQuantity
  for (const deposit of deposits) {
    if (remaining <= 0) break;
    const deductQty = Math.min(remaining, Number(deposit.remainingQuantity));
    if (deductQty <= 0) continue;
    await this.prisma.waterBottleDeposit.update({
      where: { id: deposit.id },
      data: { remainingQuantity: { decrement: deductQty } },
    });
    remaining -= deductQty;
  }

  // Phase 2: 數量不足時按單價從 remainingAmount 換算扣除
  if (remaining > 0) {
    for (const deposit of deposits) {
      if (remaining <= 0) break;
      const availableAmount = Number(deposit.remainingAmount);
      if (availableAmount <= 0) continue;
      const unitPrice = Number(deposit.quantity) > 0
        ? Number(deposit.amount) / Number(deposit.quantity)
        : 0;
      if (unitPrice <= 0) continue;
      const deductAmount = Math.min(remaining * unitPrice, availableAmount);
      await this.prisma.waterBottleDeposit.update({
        where: { id: deposit.id },
        data: { remainingAmount: { decrement: deductAmount } },
      });
      remaining -= deductAmount / unitPrice;
    }
  }
}
```

> 邏輯與 `orders.service.ts` 的 `deductWaterBottleDeposit` 完全一致，不需修改 Module 或注入其他 Service。

## 問題五：`strandedQuantity` 兩個 API 的計算鏈互相獨立，導致數值不一致

### 觀察到的行為

- `GET /delivery-reports/{id}` → `items[0].strandedQuantity = 2`
- `GET /customers/{id}/water-bottle-deposits` → `strandedQuantity = 12`

同一個客戶、同一個商品，兩個 API 回傳的滯留數量完全不同。

### 根本原因

兩個 API 使用**完全不同的資料來源**計算 `strandedQuantity`：

| API | 計算來源 | 程式位置 |
|-----|---------|---------|
| `POST /delivery-reports`（建立時計算） | 查前一筆 `DeliveryReportItem.strandedQuantity` | `delivery-reports.service.ts` ~第 647 行 |
| `GET /customers/:id/water-bottle-deposits` | 查最新 `OrderItem.strandedQuantity` | `customers.service.ts` ~第 765 行 |

這兩條計算鏈是獨立的：
- DR 計算只看歷史 DR 紀錄，不看 OrderItem
- water-bottle-deposits 只看 OrderItem，不看 DR 紀錄

當有任何一筆訂單不是透過 `convertToOrder` 建立（例如直接在訂單頁建立），或兩條鏈的數值曾經不同步，之後就會永久分叉。

### 建議修正

修改 `delivery-reports.service.ts` 建立 DR item 時，計算 `previousStranded` 的邏輯：
**同時查詢前一筆 DeliveryReportItem 和前一筆 OrderItem，取時間較新的那筆**。

```typescript
// 查前一筆 DeliveryReportItem
const lastDRItem = await this.prisma.deliveryReportItem.findFirst({
  where: {
    customerId: customer.id,
    productId: product.id,
    deliveryReport: { reportDate: { lte: new Date(reportDate) } },
  },
  orderBy: [{ deliveryReport: { reportDate: 'desc' } }, { createdAt: 'desc' }],
  select: { strandedQuantity: true, createdAt: true },
});

// 查前一筆 OrderItem（直接建立的訂單也要算進來）
const lastOrderItem = await this.prisma.orderItem.findFirst({
  where: {
    order: {
      customerId: customer.id,
      orderDate: { lte: new Date(reportDate) },
    },
    productId: product.id,
  },
  orderBy: { order: { orderDate: 'desc' } },
  select: { strandedQuantity: true, createdAt: true },
});

// 取時間較新的那筆作為基準
let previousStranded = 0;
if (lastDRItem && lastOrderItem) {
  previousStranded = lastDRItem.createdAt > lastOrderItem.createdAt
    ? Number(lastDRItem.strandedQuantity)
    : Number(lastOrderItem.strandedQuantity);
} else if (lastDRItem) {
  previousStranded = Number(lastDRItem.strandedQuantity);
} else if (lastOrderItem) {
  previousStranded = Number(lastOrderItem.strandedQuantity);
}

const strandedQuantity = Math.max(0, previousStranded + item.quantity - recoveredQuantity);
```

這樣兩條計算鏈就會合一，DR 建立時也會正確累計從訂單來的滯留數量。
