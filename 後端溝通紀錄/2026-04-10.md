## 📐 儲值扣除計算邏輯說明

延續 [2026-04-09](./2026-04-09.md) 討論的 `deductWaterBottleDeposit` Phase 2 問題，以下說明前端目前採用（也是預期後端應實作）的正確計算邏輯。

### 計算規則

```
1. 先從 remainingQuantity 扣（訂購數量）
2. 若數量不夠（溢出），用 remainingAmount 補：
   可補桶數 = floor(remainingAmount / 單價)
   實際補桶數 = min(溢出桶數, 可補桶數)
3. 若金額也補不夠 → 剩餘溢出桶數讓 remainingQuantity 變負數
4. remainingAmount 永遠 ≥ 0（不會是負數）
```

### 算式範例（儲值數量 5、儲值金額 $100、商品單價 $78）

| 訂購數量 | 溢出桶數 | 金額可補桶數 | 實際補桶數 | 剩餘數量 | 剩餘金額 | 說明 |
|---------|---------|------------|---------|---------|---------|------|
| 3 | 0 | — | — | **2** | **$100** | 數量夠，金額完全不動 |
| 5 | 0 | — | — | **0** | **$100** | 數量剛好用完，金額完全不動 |
| 6 | 1 | floor(100/78) = **1** | 1 | **0** | **$22** | 金額蓋掉 1 桶，數量不變負 |
| 7 | 2 | floor(100/78) = **1** | 1 | **-1** | **$22** | 金額只蓋 1 桶，剩 1 桶蓋不住 → 負數 |
| 10 | 5 | floor(100/78) = **1** | 1 | **-4** | **$22** | 溢出 5 桶，金額蓋 1 桶，剩 4 桶變負數 |
| 100 | 95 | floor(100/78) = **1** | 1 | **-94** | **$22** | 嚴重超量，金額仍只蓋 1 桶 |

### 特殊情境

| 情境 | 儲值金額 | 單價 | 訂購 | 剩餘數量 | 剩餘金額 | 說明 |
|------|---------|------|------|---------|---------|------|
| 金額不足蓋一桶 | $50 | $78 | 6 | **-1** | **$50** | floor(50/78) = 0，金額一桶都補不了 |
| 金額恰好蓋完 | $156 | $78 | 7 | **0** | **$0** | floor(156/78) = 2，蓋掉溢出的 2 桶，金額歸零 |

### 關鍵結論

- **`remainingAmount` 永遠不會是負數**（用 floor 取整，只扣整桶的金額）
- **`remainingQuantity` 才會是負數**（代表超出儲值的桶數）
- 金額不足以蓋一整桶時（`單價 > remainingAmount`），金額保留不動，超出的桶直接讓數量變負數

## 🐛 發現問題：Phase 2 單價來源錯誤

### 問題描述

後端工程師今天（2026-04-10）已修復 Phase 2 Dead Code，三個 Phase 目前都會執行。但驗證後發現 **Phase 2 的單價計算來源有誤**。

**現行程式碼（`orders.service.ts` ~line 1303）：**
```ts
const originalQty = Number(deposit.quantity);
const unitPrice = originalQty > 0 ? Number(deposit.amount) / originalQty : 0;
```

後端用 **儲值紀錄本身的 `amount ÷ quantity`** 來推算單價，而不是商品的實際售價。

### 問題範例

條件：儲值數量 5、儲值金額 $100、商品實際單價 $78、訂購 6 桶

| 情況 | 後端推算單價 | 後端計算結果 | 正確預期結果 |
|------|------------|------------|------------|
| deposit.quantity=5, deposit.amount=100 | $100÷5 = **$20** | 0桶 / **$80** | 0桶 / **$22** |
| deposit.quantity=5, deposit.amount=0（純桶數） | $0 → 跳過 Phase 2 | **-1桶** / $100 | 0桶 / $22 |
| deposit.quantity=0, deposit.amount=100（純金額） | $0 → 跳過 Phase 2 | **-1桶** / $100 | 0桶 / $22 |

### 正確做法

Phase 2 的單價應該從**商品的實際售價**取得，而非從儲值紀錄推算。建議後端在呼叫 `deductWaterBottleDeposit` 時傳入商品單價：

```ts
// 目前
await this.deductWaterBottleDeposit(customerId, productId, quantity);

// 建議改為
await this.deductWaterBottleDeposit(customerId, productId, quantity, unitPrice);
```

`deductWaterBottleDeposit` 的 Phase 2 改用傳入的 `unitPrice`，而不是從 deposit 記錄推算：

```ts
// 移除這兩行
const originalQty = Number(deposit.quantity);
const unitPrice = originalQty > 0 ? Number(deposit.amount) / originalQty : 0;

// 改用傳入的 unitPrice 參數
```

## 🌐 前端環境檔說明

前端專案（`egg_crm_vue`）依照不同環境有對應的設定檔與 build 指令。

### 環境檔對照

| 環境檔 | 對應指令 | 連接的 API |
|--------|---------|-----------|
| `.env.development` | `npm run dev` | 測試站（透過本地 proxy 轉發） |
| `.env.staging` | `npm run build:staging` | 測試站（直接連線） |
| `.env.production` | `npm run build` / `npm run build:prod` | 正式站（直接連線） |

### API 位址

| 環境 | API Domain |
|------|-----------|
| 測試站 | `https://staging-api-staging-07d7.up.railway.app` |
| 正式站 | `https://eggdrop.up.railway.app` |

### 說明

- **本地開發（`npm run dev`）**：透過 Vite proxy 將 `/hostApi` 轉發到測試站，避免 CORS 問題
- **`build:staging`**：打包後直接連測試站 API，用於部署測試版前端
- **`build` / `build:prod`**：打包後連正式站 API，用於正式部署
