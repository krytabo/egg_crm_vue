## 問題一：從未建立儲值記錄，訂單的滯留數量看得到嗎？

### 結論

**看不到。**

`GET /customers/{id}/water-bottle-deposits` 的查詢邏輯是：
1. 先從 `WaterBottleDeposit` 表撈出該客戶**有儲值記錄**的商品
2. 再依商品 ID 去查最新 `OrderItem.strandedQuantity` 貼附上去

`strandedQuantity` 本身**確實有存入資料庫**（存在 `OrderItem` 表，每次下訂單都會計算，與是否有儲值記錄完全無關）。  
但因為查詢入口是 `WaterBottleDeposit` 表，沒有儲值記錄的商品**永遠不會出現在回傳結果中**。

## 問題二：儲值 A×5、B×2，訂單出貨 A×2、B×3、C×5，各商品狀態為何？

### 情境說明

| 商品 | 儲值數量 | 訂單出貨數量 | 回收數量 |
|------|---------|------------|---------|
| 商品A | 5 | 2 | 0 |
| 商品B | 2 | 3 | 0 |
| 商品C | 無 | 5 | 0 |

### 計算結果

| 商品 | strandedQuantity | remainingQuantity（剩餘儲值） | 是否出現在 API 回傳 |
|------|-----------------|----------------------------|------------------|
| 商品A | **2**（0+2-0） | **3**（5-2） | ✅ 出現 |
| 商品B | **3**（0+3-0） | **0**（2-3，最多扣到0） | ✅ 出現（但剩餘為0，1桶超出儲值無法扣除） |
| 商品C | **5**（存入 OrderItem，但無儲值記錄） | — | ❌ **不出現** |

> 商品B 超出儲值數量的部分（1桶）不會產生負數，直接截斷為 0，也不會有任何錯誤提示。

## 問題三：可否只有選「預付」付款方式才扣儲值？

### 目前後端行為

**目前所有客戶訂單，不論付款方式為何（現金、月結、預付），都會扣除 `WaterBottleDeposit`。**

相關程式碼（`orders.service.ts` 約第 244 行）：
```typescript
// 10. Deduct water bottle deposits for customer orders (FIFO)
if (customerId) {   // ← 只判斷是否為客戶訂單，完全不看付款方式
  for (const item of createOrderDto.items) {
    await this.deductWaterBottleDeposit(customerId, item.productId, item.quantity);
  }
}
```

### 建議修改

若業務邏輯是「只有預付才使用儲值桶」，後端只需加一個條件判斷：

```typescript
if (customerId && createOrderDto.paymentTerm === 'PREPAID') {
  for (const item of createOrderDto.items) {
    await this.deductWaterBottleDeposit(customerId, item.productId, item.quantity);
  }
}
```

同樣地，`PATCH /orders/:id` 的扣除/退回邏輯也需要同步加上此條件。

> ⚠️ 此為需求確認項目，請後端工程師依照業務規則決定是否實作。

## 問題四：預付訂單超出儲值數量，以及後續補建儲值記錄的行為

### 情境

| 商品 | 儲值數量 | 預付訂單出貨數量 |
|------|---------|--------------|
| 商品A | 5 | 10 |
| 商品B | 無 | 10 |

### 商品A 結果

| 欄位 | 值 | 說明 |
|------|---|------|
| strandedQuantity | **10** | 正常計算存入 OrderItem |
| remainingQuantity | **0** | 5桶扣完截斷為0，超出的5桶無法扣除 |

### 商品B 結果（無儲值記錄）

- `strandedQuantity = 10`（有存入 OrderItem，資料正確）
- 但 `GET /customers/{id}/water-bottle-deposits` **找不到商品B**

#### 後續補建儲值記錄的問題

若事後手動新增商品B儲值=10，**目前 `createDeposit` 不會自動回溯扣除過去的預付訂單**：

```typescript
// customers.service.ts createDeposit()
remainingQuantity: dto.quantity,  // 直接設為輸入值，不查歷史訂單
```

結果：`remainingQuantity = 10`（應為 0，因為已有10桶預付出去）。

> ⚠️ **這是一個設計缺口**：補建儲值記錄後，`remainingQuantity` 數字會不正確（偏高）。

### 建議

`createDeposit` 在建立時，若該商品有過去未扣除的預付訂單，應自動計算應扣數量並設定正確的 `remainingQuantity`。

## 問題五（補充）：預付訂單超出儲值時，`remainingQuantity` 應允許負數

### 問題背景

目前 `deductWaterBottleDeposit` 的邏輯是「最多扣到 0，不會產生負數」：

```typescript
const available = Number(deposit.remainingQuantity);
const deductAmount = Math.min(remainingToDeduct, available);  // 最多扣到0
```

### 建議行為

當付款方式為「預付」時，`remainingQuantity` 應允許出現**負數**：

| 情境 | 現有行為 | 建議行為 |
|------|---------|---------|
| 預付，出貨10，儲值只剩5 | remainingQty = 0，超出的5桶消失 | remainingQty = **-5**，明確顯示欠了5桶 |
| 預付，無儲值記錄，出貨10 | 不扣除，無紀錄 | remainingQty = **-10**（需配合問題六的虛擬列） |

### 意義

負數的 `remainingQuantity` 等同於**超賣警示**：
- 業主可以在儲值頁面直接看到哪個客戶、哪個商品的剩餘數量為負
- 負數代表「該客戶預付出貨但儲值不足，必須盡快補建儲值記錄」
- 若問題四（補建儲值時自動回溯扣除）解決後，業主補建儲值，`remainingQuantity` 就會從負數自動回歸正確值

### 與問題四的關聯

兩個需求互補：

```
問題四解決：補建儲值時，自動扣除過去預付訂單欠下的數量
問題五解決：預付訂單出貨時，超出儲值部分產生負數而非截斷為 0

合併效果：
  出貨時 → remainingQty 可能變負（提醒超賣）
  補儲值時 → 自動從負數回補到正確剩餘值
```

### 建議修改範圍

- `customers.service.ts` 的 `deductDeposit()` / `deductWaterBottleDeposit()`：移除 `Math.min` 截斷，允許最後結果為負數
- 前端儲值頁面：負數以紅色警示顯示，提醒業主需補儲值

> ⚠️ 此為功能需求建議，需後端工程師評估是否允許 `remainingQuantity` 欄位儲存負數（確認 DB schema 是否有限制）。

## 問題六：建議 API 直接回傳「桶裝水」類別的所有商品，包含未儲值商品

### 問題背景

目前 `GET /customers/{id}/water-bottle-deposits` 的最大限制：只能查到「有建立 `WaterBottleDeposit` 的商品」，查詢入口是 `WaterBottleDeposit` 表，沒有儲值記錄的商品永遠不出現。

### 已確認的後端現況

查看 `customers.service.ts` 的 `getDeposits()` 方法，確認現況：

```typescript
// 目前查詢邏輯（約第 745 行）
this.prisma.waterBottleDeposit.findMany({
  where: { customerId: customer.id },  // ← 入口是 WaterBottleDeposit 表
  include: { product: { ... } },
})
// 只有有儲值紀錄的商品才會出現
```

後端商品系統中，「桶裝水」類別的識別方式：
- `Product.categoryId` 存的是 `BusinessCategory` 的動態 UUID（非固定值）
- `BusinessCategory` 有固定的 `code` 欄位，桶裝水為 `code = 'WATER'`（在 `seed.ts` 確認）
- 因此正確的篩選方式是**透過 relation join**：`product.category.code = 'WATER'`，而不是直接比對 `categoryId` 的 UUID 值

Prisma 查法：
```typescript
where: {
  category: { code: 'WATER' }  // 透過 relation join BusinessCategory
}
```

目前共有 `WATER`（桶裝水）、`EGG`（雞蛋）、`EQUIPMENT`（飲水機）等類別。

### 建議改法

修改 `customers.service.ts` 的 `getDeposits()` 查詢邏輯，**改以「桶裝水類別所有商品」為起點**，再 LEFT JOIN 儲值記錄：

**現況：**
```
起點：WaterBottleDeposit 表（只有有儲值的商品）
附加：找對應 OrderItem 的 strandedQuantity
```

**建議改為：**
```
起點：Product 表，篩選 category.code = 'WATER' 的所有商品（共N個）
      （透過 Product → BusinessCategory relation join，非直接比對 categoryId UUID）
LEFT JOIN：WaterBottleDeposit（該客戶，該商品）
附加：找對應 OrderItem 的 strandedQuantity
```

回傳格式不變，無儲值記錄的商品以預設值填充：

| 欄位 | 有儲值記錄 | 無儲值記錄（虛擬列） |
|------|----------|------------------|
| id | 實際 deposit ID | `null`（或虛擬） |
| quantity（儲值量） | 實際儲值量 | **0** |
| amount（儲值金額） | 實際儲值金額 | **0** |
| remainingQuantity | 實際剩餘量 | **0** |
| remainingAmount | 實際剩餘金額 | **0** |
| strandedQuantity | 最新 OrderItem | 最新 OrderItem（或 0） |

### 效果舉例

系統目前有 10 個桶裝水商品，對於任何一位客戶呼叫此 API：
- **不論是否有任何儲值紀錄，都回傳這 10 筆**
- 有訂單但沒儲值的商品：`remainingQuantity=0, strandedQuantity=實際值`
- 完全沒任何紀錄的商品：所有欄位預設 0
- 之後系統新增第 11 個桶裝水商品 → 下次呼叫 API 自動出現，無需手動建立儲值記錄

### 可解決的問題

1. ✅ 無法查到沒儲值商品的滯留數量
2. ✅ 新增商品後自動出現，不需要每位客戶分別手動建立儲值記錄
3. ✅ 補建儲值記錄時能預先看到歷史滯留量，協助判斷應補多少
4. ✅ 讓水桶庫存頁面呈現完整商品全貌

### 建議修改範圍

- `customers.service.ts` 的 `getDeposits()` 方法：查詢邏輯重構，約 30-40 行變更
- 分頁的 `total` 數量邏輯需改為計算「桶裝水商品總數」

> ⚠️ 此為功能需求建議，需後端工程師評估實作。改法需特別注意分頁邏輯（total 以商品數量為準，而非 WaterBottleDeposit 筆數）。
