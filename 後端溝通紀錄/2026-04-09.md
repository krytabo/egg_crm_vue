## 問題一：`deductWaterBottleDeposit` Phase 2 金額扣除為 Dead Code

### 背景

延續 [2026-04-08 問題五](./2026-04-08.md)（`remainingQuantity` 允許負數）以及 [2026-04-03](./2026-04-03.md) Bug 5（`PATCH /orders/:id` 未調整 `remainingQuantity`/`remainingAmount`）的討論，今日在 Code Review 中發現 `orders.service.ts` 的 `deductWaterBottleDeposit()` 內有邏輯順序錯誤。

### 問題說明

`orders.service.ts` 的 `deductWaterBottleDeposit()` 分為兩個 Phase：

```typescript
// Phase 1: Deduct from remainingQuantity (FIFO, allows negative on last deposit)
for (const deposit of deposits) {
  // ... 扣 remainingQuantity
  remaining -= deductQty;
}

// If still remaining after all positive deposits, push excess onto last deposit (negative)
if (remaining > 0 && deposits.length > 0) {
  // ... 直接讓最後一筆 remainingQuantity 變負數
  remaining = 0;  // ← 問題在這裡：remaining 被強制歸零
}

// Phase 2: If quantity still not covered, deduct from remainingAmount
if (remaining > 0) {  // ← 這個條件永遠是 false，Phase 2 從不執行
  // ... 扣 remainingAmount（Dead Code）
}
```

**原因：** Phase 1 之後的「push to negative」block 在 Line 1304 把 `remaining = 0`，導致緊接著的 Phase 2 `if (remaining > 0)` 永遠進不去。

### 實測情境

| 條件 | 期望結果 | 目前實際結果 |
|------|---------|------------|
| 儲值數量 19、儲值金額 $1500、商品單價 $85、訂購 20 | qty=**0** / amt=**$1415** | qty=**-1** / amt=**$1500** |
| 儲值數量 19、儲值金額 $1500、商品單價 $85、訂購 36 | qty=**0** / amt=**$55** | qty=**-17** / amt=**$1500** |
| 儲值數量 19、儲值金額 $1500、商品單價 $85、訂購 37 | qty=**-1** / amt=**$55** | qty=**-18** / amt=**$1500** |

> 商品單價 $85，金額 $1500 最多能蓋 `floor(1500 / 85) = 17` 桶。
> 訂購 37 時：數量扣 19 桶後溢出 18 桶，金額蓋 17 桶（$1445），差 1 桶才讓數量變 -1，剩餘金額 $55。

## 問題二：預期扣除順序

### 期望的正確邏輯順序

```
1. 先從 remainingQuantity 扣（FIFO，只扣正數的 deposit）
2. 若仍有剩餘（overflow）→ 用 remainingAmount 去補（overflow × 單價，floor 除法）
3. 若金額也補不夠 → 才讓最後一筆 remainingQuantity 變負數
4. remainingAmount 永遠 ≥ 0（不允許負數）
```

### 建議修法

將「push to negative」block 移到 Phase 2 **之後**，讓 Phase 2 有機會執行：

```typescript
// Phase 1: Deduct from remainingQuantity (FIFO)
for (const deposit of deposits) {
  if (remaining <= 0) break;
  const availableQty = Number(deposit.remainingQuantity);
  if (availableQty <= 0) continue;
  const deductQty = Math.min(remaining, availableQty);
  // ... update DB
  remaining -= deductQty;
}

// Phase 2: 數量不夠時，用 remainingAmount 補
if (remaining > 0) {
  for (const deposit of deposits) {
    if (remaining <= 0) break;
    const availableAmount = Number(deposit.remainingAmount);
    if (availableAmount <= 0) continue;
    const originalQty = Number(deposit.quantity);
    const unitPrice = originalQty > 0 ? Number(deposit.amount) / originalQty : 0;
    if (unitPrice <= 0) continue;
    const bottlesCoverable = Math.floor(availableAmount / unitPrice);
    const covered = Math.min(remaining, bottlesCoverable);
    const deductAmount = covered * unitPrice;
    // ... update DB: remainingAmount decrement deductAmount
    remaining -= covered;
  }
}

// Phase 3: 數量和金額都不夠 → 讓最後一筆 remainingQuantity 變負數
if (remaining > 0 && deposits.length > 0) {
  const lastDeposit = deposits[deposits.length - 1];
  // ... update DB: remainingQuantity decrement remaining
  remaining = 0;
}
```

> 注意：Phase 2 原本是用 `amountNeeded = remaining * unitPrice`，然後 `Math.min(amountNeeded, availableAmount)`。
> 但這樣可能產生非整數的「蓋了幾桶」（`deductQtyByAmount = deductAmount / unitPrice`），建議改用 `Math.floor` 確保整數桶數，剩餘金額也比較乾淨。

## 補充：前端目前的假計算邏輯

前端在下單視窗選擇商品數量時，會即時顯示「下單後預估的剩餘儲值狀況」（假計算，實際以後端為準）。

目前前端採用的計算邏輯與**期望的正確邏輯一致**（先扣數量，再扣金額，最後才讓數量變負）。一旦後端修正 Phase 2，前後端的行為就會對齊。
